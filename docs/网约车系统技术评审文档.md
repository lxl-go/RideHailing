## 一、整体技术架构总览

### 1. 三端架构分层总览

系统采用物理三端隔离、逻辑数据中台的分层架构：

```
┌──────────────────────────────────────────────────────────────────┐
│                        接入层 (API Gateway)                        │
│  Nginx/OpenResty → 统一鉴权 → 限流 → 路由转发                     │
├─────────────┬───────────────────────┬────────────────────────────┤
│  管理端 Web   │   乘客端                  │   司机端                    │
│  Vue3+EP    │   UniApp（Vue3）         │   UniApp（Vue3）            │
│  :5173      │   H5/小程序/App          │   H5/小程序/App             │
├──────┬──────┴──────┬───────────────┴──┬─────────────────────────┤
│  管理端 API      │  乘客端 API         │  司机端 API                │
│  Gin+GVA        │  Kratos v3          │  Kratos v3                │
│  :8888          │  :8081              │  :8082                    │
├──────┴──────┬────┴──────────┬─────────┴──────────────────────────┤
│           服务层 (gRPC + Kafka 事件总线)                          │
│  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐        │
│  │ 认证服务 │ │ 订单服务 │ │ 支付服务 │ │ 派单服务 │ │ 消息服务 │ ...  │
│  └────────┘ └────────┘ └────────┘ └────────┘ └────────┘        │
├──────────────────────────────────────────────────────────────────┤
│                        数据层                                     │
│  MySQL(主)  Redis(缓存+GEO)  ES(搜索)  MongoDB(轨迹)  Kafka(事件) │
└──────────────────────────────────────────────────────────────────┘
```

管理端、乘客端、司机端各有独立的 API 部署单元和前端部署单元。微服务层共享同一套服务集群，通过 gRPC 进行内部通信，通过 Kafka 事件总线解耦跨端状态同步。三端通过 API Gateway 统一接入，Gateway 层负责鉴权验签、流量控制、请求路由。

### 2. 微服务拆分与服务治理方案

服务拆分遵循「按业务域拆分+按终端聚合」的原则，共拆分为以下微服务：

| 服务名 | 归属域 | 协议 | 依赖 | 核心职责 |
|--------|-------|------|------|---------|
| admin-api | 管理端 | HTTP(RESTful) | 全部下游 gRPC 服务 | 管理端聚合层，提供统一 RESTful 接口，调用微服务层 |
| passenger-api | 乘客端 | HTTP(gRPC-Gateway) | order/user/message/ai 服务 | 乘客端 API 聚合，WebSocket 连接管理 |
| driver-api | 司机端 | HTTP(gRPC-Gateway) | order/user/dispatch/location 服务 | 司机端 API 聚合，WebSocket 连接管理 |
| user-svc | 通用 | gRPC | MySQL/Redis | 用户注册/登录/实名认证/角色权限 |
| order-svc | 订单 | gRPC | MySQL/Redis/Kafka | 订单 CRUD/状态机/退票/评价 |
| dispatch-svc | 派单 | gRPC | Redis/MySQL/Kafka | 派单引擎/规则管理/多维评分/灰度发布 |
| payment-svc | 支付 | gRPC | MySQL/Redis/Kafka | 支付/退款/对账/账单/争议 |
| shuttle-svc | 班车 | gRPC | MySQL/Redis/ES | 班线/班次/排班/站点/地图 |
| marketing-svc | 营销 | gRPC | MySQL/Redis | 优惠券/活动/发放规则/推荐奖励 |
| analytics-svc | 数据 | gRPC | MySQL | 订单量/转化率/复购/行为分析（MySQL 聚合查询） |
| location-svc | 位置 | gRPC+WS | Redis GEO/MongoDB | 司机位置上报/GEO查询/轨迹回放 |
| ai-svc | AI | gRPC | Coze API/Redis | 天气预警/AI对话/路线计算/积水识别 |
| message-svc | 消息 | gRPC | Kafka/WebSocket | 实时推送/系统通知/消息路由 |
| job-svc | 调度 | HTTP | cron/MySQL | 定时任务/对账任务/ETL任务/排班任务（Go cron 原生实现） |

服务治理方案：
- **注册与发现**：Kratos 内置服务发现 + 直接配置直连地址（开发环境简化，生产环境可引入 Consul/etcd）
- **负载均衡**：Kratos 内置的加权轮询 + 熔断（连续5次失败熔断30秒）
- **配置中心**：三端统一接入 Nacos，命名空间 `public`、Group `DEFAULT_GROUP`、Data ID `ride-car`、格式 YAML；本地 `config.yaml` 仅作为开发和 Nacos 不可用时的兜底配置，业务热配置通过 Nacos/数据库配置表双通道刷新
- **链路追踪**：基于 OpenTelemetry，接入 Jaeger，全链路追踪 ID 透传
- **日志采集**：Zap → Loki → Grafana，结构化 JSON 格式，每行包含 trace_id + span_id + service_name

**索引策略**：
- `certification_audit` 表：`(status, created_at)` 联合索引用于待审核列表查询（管理员按状态筛选）；`(user_id)` 索引用于查询用户认证历史。
- `trip` 表：`(departure_time, status)` 联合索引用于行程列表筛选；`(origin_lat, origin_lng)` 空间索引用于附近行程 GEO 查询；`(publisher_id)` 索引用于用户个人行程查询。
- 使用 InnoDB 引擎，所有表 utf8mb4 字符集。

**【新增】主键生成策略**：

| 策略 | 适用场景 | 说明 |
|------|---------|------|
| **雪花算法（Snowflake）** | 全部核心业务主表 | order_main、driver_info、vehicle_info、certification_audit、trip、transaction_ledger、coupon_template、dispatch_log 等所有需要跨服务引用或分库分表的表 |
| 数据库自增 ID | 仅本地中间临时表、日志归档子表、单库静态配置表（字典表） | order_status_log（日志性质）、配置字典表等无需跨服务引用的表 |
| UUID | **禁止使用** | 无序导致 InnoDB 索引页分裂严重，索引性能差；占用 128bit 存储空间大 |

**雪花 ID 结构**（64 bit long）：
```
 0 | 41 bit 时间戳 | 10 bit 工作节点ID | 12 bit 序列号
```
- 时间戳：自定义起始时间（如 2026-01-01）起的毫秒数，可用约 69 年
- 工作节点ID：服务标识 + 进程标识（通过统一 ID 分发服务分配）
- 序列号：同一毫秒内最多 4096 个 ID

**分布式 ID 生成组件部署方案**：

| 组件 | 职责 | 部署方式 |
|------|------|---------|
| ID 分发服务 | 管理各服务的 WorkerID 分配，监控时钟回拨 | 独立微服务（轻量 HTTP），启动时获取一次 |
| Snowflake 本地库 | 各服务内嵌的 ID 生成库，本地缓存 WorkerID | Go module：`internal/infrastructure/id/snowflake.go` |
| 时钟回拨处理 | 回拨 < 1s 等待，≥ 1s 阻塞并告警 | Snowflake 库内置回拨检测 |

```go
// 雪花算法 Go 实现核心约束（见 code_arch_rule.md 完整实现）
type Snowflake struct {
    mu           sync.Mutex
    epoch        int64           // 自定义起始时间戳
    nodeID       int64           // 工作节点 ID（通过分发服务获取）
    sequence     int64           // 当前毫秒序列号
    lastTimestamp int64          // 上次生成 ID 的时间戳
}
```

**各核心表主键生成方案对照**：

| 表名 | PK 类型 | 生成策略 | 理由 |
|------|--------|---------|------|
| order_main | bigint PK | 雪花 ID | 分布式多服务创建订单，分库分表核心表 |
| driver_info | bigint PK | 雪花 ID | 跨服务引用（dispatch/order/payment），数据量大 |
| vehicle_info | bigint PK | 雪花 ID | 引用 driver_info，跨服务 |
| certification_audit | bigint PK | 雪花 ID | 跨 user-svc/audit 引用 |
| trip | bigint PK | 雪花 ID | 多端（passenger/driver）发布，核心业务表 |
| transaction_ledger | bigint PK | 雪花 ID | 财务核心表，分月分表 |
| coupon_template | bigint PK | 雪花 ID | 跨 marketing-svc/order-svc 引用 |

| sys_dict / sys_config | int (自增) | 自增 ID | 单库静态配置表，少数据量，无跨服务引用 |

#### 3. 接口出入参规范

**审核列表查询** `GET /api/v1/carpool/audits`

入参：
```json
{
  "status": 0,
  "cert_type": 1,
  "start_time": "2026-07-01T00:00:00Z",
  "end_time": "2026-07-22T00:00:00Z",
  "keyword": "138****1234",
  "page": 1,
  "page_size": 20,
  "idempotent_key": "uuid"  // 幂等键（写操作必传）
}
```

出参：
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "list": [
      {
        "id": 10001,
        "user_id": 5001,
        "real_name": "张三",
        "cert_number": "41**************1234",
        "status": 0,
        "created_at": "2026-07-21T14:30:00Z"
      }
    ],
    "total": 128,
    "page": 1,
    "page_size": 20
  }
}
```

统一状态码：`0=成功` `10001=参数错误` `10002=无权限` `10003=资源不存在` `20001=业务规则拦截` `50000=系统错误`。

#### 4. 服务交互流程

```
管理端 API 请求 → Gin 路由 → AuthMiddleware 鉴权 → 参数校验(Validator)
    → Controller → Service → Gorm 查询/写入 MySQL
    → 审核操作触发消息 → Kafka Topic: cert_audit_result
    → passenger-api 消费 → 推送审核结果通知给乘客/司机
```

操作日志写入使用 GVA 内置的 `operation_record` 中间件，自动记录请求路径、参数、操作人、IP。

#### 5. 异常处理方案

| 异常场景 | 处理逻辑 | 用户反馈 |
|---------|---------|---------|
| 证件OCR识别失败 | 允许管理员手动填写证件信息 | 前端展示OCR识别失败提示 |
| 审核超时48小时 | 定时任务扫描 → 升级通知超管 | 超管收到待审核清单通知 |
| 照片上传失败 | 前端分片上传+断点续传 | 进度条+重试按钮 |
| 重复注册检测 | 身份证号UK检查，冲突时提示 | 页面高亮「疑似重复」 |

#### 6. 性能保障方案

- 审核列表页：MySQL `(status, created_at)` 复合索引 + 分页查询，目标 QPS≥500
- 证件图片：上传至 OSS，采用 CDN 加速访问，数据库仅存 URL
- 审核统计缓存：Redis String 缓存各类状态计数，审核操作后主动更新缓存
- 批量导出：异步任务生成 Excel 文件，完成后通知下载（避免 HTTP 超时）

#### 7. 潜在风险与应对

| 风险 | 应对措施 |
|------|---------|
| OCR 识别准确率不足（生僻字/模糊照片） | 保留人工修正入口，管理员可编辑 OCR 识别结果 |
| 证件照片隐私泄露 | 全链路 HTTPS + 图片 URL 鉴权（临时签名） + 数据库加密存储证件号（AES-256） |
| 审核任务堆积（节假日高峰期） | 按 `status=0` 优先级队列消费，高峰期自动扩容审核线程池 |

#### 5. 异常处理方案

| 异常场景 | 处理逻辑 | 用户反馈 |

#### 6. 性能保障方案

- 排班冲突校验：Redis 缓存司机当日排班时间窗 ZSet，O(logN) 查询
- 班线列表：MySQL 分页查询 + Redis 缓存热门班线列表（TTL 5分钟）
- 站点排序：应用层保存时一次写入排序，后续查询按 `sort_order` 升序读取
- 地图加载：首次加载后缓存路线经纬度数组到 Redis，避免重复查询数据库

| 风险 | 应对措施 |

#### 4. 服务交互流程

```
支付回调 → Kafka Topic: payment_result
    → payment-svc 消费 → 写入 transaction_ledger
    → 每日凌晨 cron 定时任务触发对账
    → 读取前一日支付平台流水（CSV/API） → 逐笔匹配
    → 差异写入对账差异表 → 推送财务岗通知
    → 每月1日触发账单任务 → 汇总司机/乘客账单 → 双端推送
```

对账核心逻辑：以支付平台流水为基准，与系统 `transaction_ledger` 逐笔按 `order_id` 精确匹配。系统有但平台无 → 标记「系统多笔」；平台有但系统无 → 标记「平台多笔」；金额不一致 → 标记「金额差异」。

#### 5. 异常处理方案

| 异常场景 | 处理逻辑 |
|---------|---------|
| 支付平台流水文件获取失败 | Job 重试3次（间隔30分钟），仍失败发告警通知财务岗手工导入 |
| 单笔对账差异≥1000元 | 自动标记「需人工复核」，不进入自动处理流程 |
| 退款失败 | 接口重试3次（间隔5分钟），失败生成人工处理工单 |
| 并发对账 | Redis 分布式锁 `lock:reconciliation:date`，防止同一日重复对账 |

#### 6. 性能保障方案

- 对账任务：按月分表查询 + 批量处理（每次 Batch 1000条）
- 账单生成：按司机 ID 分片并行处理 + 写入临时表后统一切换
- 交易流水查询：`(user_id, created_at)` 复合索引 + 分页
- 缓存：司机当日收入总金额缓存 Redis String（TTL 1天，订单完成后更新）

#### 7. 潜在风险与应对

| 风险 | 应对措施 |
|------|---------|
| 支付平台流水延迟或缺失 | 对账时读取平台T+2数据而不是T+1，留出延迟窗口 |
| 金额精度误差（分精度不一致） | 所有金额存储以分为单位（int64），展示时除以100 |
| 重复对账 | Redis 分布式锁 + 幂等键 + 对账批次号唯一约束 |

**状态机约束**：
```
正向流程：pending → paid → ongoing → completed
取消流程：pending → cancelled（未支付取消）

异常流程：ongoing → cancelled（司机/乘客中途取消，需退款/赔付）
           completed → refunding → refunded（完成后争议退款）
```
状态转换在 Gorm 的 `BeforeUpdate` 钩子中校验，非法转换直接返回错误。关键状态转换（paid→ongoing→completed）记录在 order_status_log 表中用于对账和争议溯源。

| 异常场景 | 处理逻辑 |
|---------|---------|
| 退票申请重复提交 | idempotent_key 幂等校验，同一 key 返回已有结果 |

| 订单状态锁定（并发修改） | Gorm 乐观锁 version 字段，version 不匹配拒绝修改 |
| 订单已完成但申请退票 | 规则拦截：「已完成订单不可退票，请联系客服」|

#### 6. 性能保障方案

- 订单列表：ES 搜索引擎承载组合搜索（QPS≥500），MySQL 作为最终数据源
- 订单详情：Redis Hash 缓存（TTL 30分钟），缓存 miss 时回源 MySQL 并回填缓存
- 退票审核：待审核队列存储在 Redis List，管理端轮询消费
- 日历视图：Redis ZSet 按发车日期索引班车订单，O(logN) 查询

#### 7. 潜在风险与应对

| 风险 | 应对措施 |
|------|---------|
| ES 与 MySQL 数据不一致 | 订单变更时双写 + 定时对账（每小时扫描不一致数据并修正） |
| 退款金额计算错误 | 退款计算逻辑单元测试覆盖率≥95%，支持人工修正入口 |
| 高并发下订单号重复 | 订单编号使用 Redis INCR + 日期前缀；**表主键统一使用雪花算法全局 ID** |

local stock = redis.call('GET', KEYS[1])

if count and tonumber(count) >= tonumber(ARGV[2]) then return -2 end
redis.call('DECR', KEYS[1])

| push_result | tinyint | KEY | 推送结果：0=已推送 1=已接单 2=已拒绝 3=超时未接 |
| response_time_sec | int | - | 司机响应耗时（秒，接单/拒绝/超时） |
| decision_reason | varchar(256) | - | 决策原因说明（如"GEO评分最高，距离2.3km"） |
| created_at | datetime | KEY | 创建时间 |

**多维评分算法**：

```
total_score = geo_score * weight_geo 
            + driver_rating * weight_rating 
            + time_window_penalty * weight_time 
            + history_accept_rate * weight_accept
```

各维度和权重从 `dispatch_rule_config.weights` 读取，支持通过管理端修改配置后实时生效（本地缓存每5分钟刷新）。灰度发布时，部分订单走新规则，部分走旧规则，对比接单率和乘客满意度。

#### 4. 服务交互流程

```
乘客下单 → order-svc → 调用 dispatch-svc
    ↓
dispatch-svc 执行规则a → 筛选候选司机池
    ↓
执行规则b → 校验时间窗冲突
    ↓
执行规则c → 按时段计算权重
    ↓

    ↓

    ↓

    ↓

    ↓

    ↓
order-svc 更新订单状态 → Kafka 事件 → 推送乘客端
    ↓
派单引擎释放司机 → 重新加入派单池 → 可接收新订单
```

#### 5. 异常处理方案

| 异常场景 | 处理逻辑 |
|---------|---------|
| 无可用司机 | 按规则 c 的超时策略扩大 GEO 搜索半径或降级规则，15分钟后通知乘客 |
| 司机已接单但锁未释放 | Redis 分布式锁 `lock:driver:{driver_id}` 设 TTL 30秒，超时自动释放 |
| 规则配置错误导致引擎崩溃 | 规则配置变更前做 schema 校验 + 配置版本管理 + 一键回滚 |
| 灰度发布异常 | 监控灰度组订单的接单率/取消率，超过阈值自动全量回滚 |

#### 6. 性能保障方案

- 派单计算：全链路在 Redis 中完成（GEO查询+ZSet排序），避免 MySQL 参与实时派单
- 候选司机池：Redis SET 维护各城市/车队的在线司机 ID 集合
- GEO 距离计算：Redis GEO 命令 O(log(N)) 复杂度，单次查询 <5ms
- 派单推送：WebSocket 长连接 + Redis Stream 做消息持久化，防止服务重启丢消息
- 派单日志：异步写入 MySQL，不阻塞主流程

#### 7. 潜在风险与应对

| 风险 | 应对措施 |
|------|---------|
| 派单引擎单点故障 | dispatch-svc 多副本部署 + Redis 持久化 + 选主机制 |
| 规则配置错误导致大面积派单异常 | 配置变更走审批流程 + 灰度发布（5%→20%→50%→100%）+ 一键回滚 |
| GEO 查询精度不足（司机位置延迟） | 司机位置上报 ≤3秒间隔 + Redis GEO 过期时间设 10秒（过期自动移除） |
| 并发派单造成重复分配 | 订单级别 Redis 分布式锁 + 司机级别分布式锁 + 15秒超时自动释放 |

**AI 工具函数注册方式（Coze Function Calling）**：
1. 在 Coze 平台创建 Bot，配置 Bot 的人设与回复逻辑（天气咨询/路线规划/积水上报）
2. 在 Bot 的「功能」中配置「插件」或「工作流」作为 Function Calling 的触发条件
3. Coze Bot 识别用户意图 → 触发 Function Calling → 通过 Web API 回调到 ai-svc 的 Go 后端函数
4. ai-svc 执行对应函数（`calculate_rain_route`、`get_weather_alert`、`report_flooding`）→ 返回结果给 Coze Bot
5. Coze Bot 用函数结果组织自然语言回复 → 通过 ai-svc 推送给用户

**Agent 工作流**：
1. **天气感知 Agent**：定时检测气象数据（cron 定时任务），触发预警 → 推送给用户
2. **对话理解 Agent**：Coze 大模型解析用户意图 → 路由到对应工具函数
3. **路线规划 Agent**：执行 Go 工具函数获取路线 → 结合天气数据优化
4. **行程保障 Agent**：异常天气下自动匹配条件车辆 → 保障乘客安全

| AI 工具函数参数解析错误 | 回复「未完全理解您的需求，请重新描述」 | 引导用户使用快捷指令 |
| 积水识别失败 | AI 置信度<80%时提示「无法确认积水深度」 | 仅上报不自动更新订单 |

#### 6. 性能保障方案

- Coze API 调用：设置超时 5 秒，超时走降级
- 对话上下文：Redis Hash 存储最近 20 轮对话（TTL 30分钟）
- 天气数据：每 15 分钟从气象 API 拉取 → 缓存到 Redis
- 路线计算：第三方地图 API 结果缓存到 Redis（相同 origin+dest 组合缓存 5 分钟）

## 五、跨模块全局技术评审

### 1. 数据一致性保障方案

**分布式事务方案**：

| 场景 | 方案 | 说明 |
|------|------|------|
| 订单创建+库存扣减 | 本地事务+消息队列 | MySQL 本地事务写入订单 → 发送 Kafka 消息 → 下游消费 |
| 退款+状态更新 | 事务性消息 | Kafka 事务消息，确保消息发送与本地事务的一致性 |
| 支付回调处理 | 幂等键+TCC | 支付回调处理前检查 idempotent_key，已处理直接返回 |
| 派单+订单锁定 | Redis 分布式锁 | `lock:order:{order_id}` + `lock:driver:{driver_id}` |

**幂等方案**：
- 所有写操作接口要求调用方传入 `idempotent_key`（UUID）
- 服务端收到请求时查 Redis `idempotent:{key}`，已存在则返回缓存结果
- TTL 设 24 小时，确保一天内的重复请求能被拦截
- 关键表增加 `idempotent_key` 字段 + 唯一索引（数据库级防重）

**缓存一致性**：缓存更新采用 Cache-Aside 模式 + 变更时主动失效 + 兜底 TTL。

**事务边界**：微服务间的事务通过 Saga 模式（编排型）实现：
- 订单创建 Saga：创建订单→扣减优惠券→扣减库存→全部成功则完成 → 任一步失败则执行补偿（取消订单+归还优惠券+恢复库存）

### 2. 统一权限与安全体系

**认证体系**：
- 管理端：JWT Token（access_token 30 分钟 + refresh_token 7 天）
- 乘客/司机端：JWT Token（access_token 7 天，移动端常用）
- Token 存储在 Redis，支持单点登录和强制下线

**AuthMiddleware 权限模型**（管理端）：
```
用户 → 角色（多对多）→ 权限（多对多）→ 资源:操作
```
AuthMiddleware 自定义中间件实现：每个数据模型结构体实现 `TableName() string` 方法绑定数据表名，中间件根据用户角色从数据库加载权限规则，自动校验对指定数据表的操作权限。权限规则存储在 MySQL 权限表中，启动时加载到内存缓存。

**安全措施**：

| 维度 | 方案 |
|------|------|
| 传输安全 | 全接口 HTTPS，HSTS 策略 |
| 防重放 | 请求时间戳 ±5 分钟 + nonce 一次性 |
| SQL 注入 | Gorm 参数绑定 + 禁止原生 SQL 拼接 |
| XSS 防护 | 前端输出 HTML 转义 + Content-Security-Policy |
| 敏感数据加密 | 身份证/手机号 AES-256 加密存储 + 展示脱敏 |
| 操作审计 | Zap 结构化日志记录所有写操作 + 审计日志表 |
| 接口限流 | Nginx limit_req + 业务层限流（按用户/按IP） |
| 防刷 | 验证码+设备指纹+行为验证（滑动/点选） |

### 3. 全链路监控与运维方案

**指标监控（Prometheus + Grafana）**：

| 指标 | 采集点 | 告警阈值 |
|------|--------|---------|
| API 响应时间 P99 | 每个接口 | >2s 告警 |
| QPS | 每个接口 | 超过基线 50% 告警 |
| 错误率 | 每个接口 | >1% 告警 |
| JVM/Go GC 暂停 | 每个服务实例 | >100ms 告警 |
| 缓存命中率 | Redis | <60% 告警 |
| MySQL 慢查询 | 数据库 | >200ms 记录慢日志 |
| Kafka 消费延迟 | 每个消费者组 | >10000 告警 |
| WebSocket 连接数 | message-svc | >80% 连接上限告警 |

**日志体系（Zap → Loki → Grafana）**：
- 每个请求生成唯一 trace_id，透传至所有下游服务
- 日志格式：`{"time":"...","level":"info","service":"order-svc","trace_id":"...","msg":"...","extra":{}}`

### 3. 连接管理方案

| 维度 | 方案 |
|------|------|
| 连接数上限 | 单机 5 万长连接，水平扩展按 `user_id % node_count` 哈希路由 |
| 心跳保活 | 客户端每 30s 发 `ping`，服务端回复 `pong`；60s 无心跳主动断开 |
| 断线重连 | 客户端指数退避重连（1s→2s→4s→...→30s max），最多 5 次 |
| 离线消息 | Redis Stream `ws:offline:{user_id}` 保存最近 100 条消息，重连后批量拉取 |
| 连接鉴权 | 建立连接时携带 JWT Token，服务端校验，鉴权失败返回 4001 关闭连接 |
| 并发关闭 | 用户重复登录 → 旧连接收到强制下线消息后自行关闭 |

### 4. 性能保障

| 维度 | 目标 | 手段 |
|------|------|------|
| 消息延迟 | P99 ≤100ms（端到端） | Redis 直推 + 无中间件中转 |

| 异常 | 处理 |
|------|------|
| 推送失败（连接已断开） | 写入离线消息队列，不阻塞主流程 |

### 2. 幂等键实现方案

```go
// 幂等校验中间件（Kratos/Gin 通用）
func IdempotentMiddleware(svc *IdempotentService) middleware.Middleware {
    return func(handler middleware.Handler) middleware.Handler {
        return func(ctx context.Context, req interface{}) (interface{}, error) {
            // 只对 POST/PUT/DELETE 生效
            if method := getMethod(ctx); !isWriteMethod(method) {
                return handler(ctx, req)
            }
            key := getIdempotentKey(req) // 从请求体获取
            if key == "" {
                return nil, status.Error(codes.InvalidArgument, "缺少幂等键 idempotent_key")
            }
            // Redis SETNX + TTL
            ok, err := svc.redis.SetNX(ctx, "idempotent:"+key, "processing", 24*time.Hour)
            if err != nil {
                return nil, err
            }
            if !ok {
                // 返回缓存结果（幂等）
                cached, _ := svc.redis.Get(ctx, "idempotent:result:"+key)
                if cached != "" {
                    return cached, nil
                }
                return nil, status.Error(codes.AlreadyExists, "请求已提交，请勿重复操作")
            }
            result, err := handler(ctx, req)
            if err == nil {
                svc.redis.Set(ctx, "idempotent:result:"+key, result, 24*time.Hour)
            } else {
                svc.redis.Del(ctx, "idempotent:"+key) // 失败时释放幂等键
            }
            return result, err
        }
    }
}
```

### 3. 分布式事务（Saga 编排型）

| Saga | 参与服务 | 正向步骤 | 补偿步骤 |
|------|---------|---------|---------|
| 订单创建 Saga | order-svc, marketing-svc, payment-svc | ①创建订单(状态=pending) ②扣减优惠券(锁定) ③扣减库存 | ①取消订单 ②归还优惠券 ③恢复库存 |

| 退款 Saga | order-svc, payment-svc | ①校验退票规则 ②调用支付平台退款 ③更新订单(refunded) ④写退款流水 | 退款失败人工处理(不自动补偿) |

## 十、班车站点复杂计算专项评审（工单 02）

### 1. 站点排序算法

```
输入：站点列表 [{id, name, lat, lng, offset_min, sort_order}, ...]
规则：
 ① 同一班线内，同一站点不可同时为上车点和下车点（应用层 + DB 唯一约束校验）
 ② 站点按 offset_min（距首站偏移分钟数）自动升序排列，首站 offset_min=0
 ③ 用户可拖拽调整站点顺序 → 重新计算 offset_min + sort_order
 ④ 站点关联班次已有排班时，删除站点前校验引用 → 提示管理员先处理排班

排序算法：
  1. 用户提交排序 ids → 校验 ids 数量和去重
  2. 按 ids 顺序重新生成 sort_order (1,2,3,...)
  3. 根据相邻站点的高德地图驾车时长重新计算 offset_min
  4. 事务提交：删除原站点排序 → 批量写入新排序 → 更新 Redis ZSet 缓存
  5. 如任一步失败 → 事务回滚 → 用户看到的仍是排序前的状态
```

### 2. 排班冲突校验算法

```
输入：driver_id, schedule_date, departure_time, duration_min
输出：冲突列表 [{conflict_schedule_id, time_range}]

算法步骤：
  1. 查 Redis ZSet key=`schedule:driver:{driver_id}:{date}`
     - score=departure_timestamp, member=schedule_id
  2. ZRANGEBYSCORE 获取该司机当日的排班时间窗
  3. 遍历已有排班，判断新班次与已有班次的时间窗是否重叠：
     - 新班次窗口 = [departure_time, departure_time + duration_min]
     - 已有班次窗口 = [existing_departure, existing_departure + existing_duration]
     - 重叠判定：新窗口.start < 已有窗口.end AND 新窗口.end > 已有窗口.start
  4. 存在重叠 → 返回冲突列表 → 管理端红色高亮
  5. 无重叠 → 写入 MySQL + 更新 Redis ZSet
  6. 并发保护：Redis 分布式锁 `lock:schedule:{driver_id}:{date}` (TTL 10s)
```

## 十一、批量退票并发场景专项评审（工单 03+04）

### 1. 退票政策阶梯规则

| 退票时机（距出发时间） | 手续费比例 | 自动审核 | 备注 |
|----------------------|-----------|---------|------|
| > 48 小时 | 免费 | 自动通过 | 全额退款，即时到账 |
| 24-48 小时 | 票价 10% | 自动通过 | 金额 ≤500 元自动，>500 元需人工 |
| 2-24 小时 | 票价 30% | 自动通过 | 金额 ≤200 元自动，>200 元需人工 |
| < 2 小时 | 票价 50% | 人工审核 | 全部进入人工队列 |
| 已发车 / 已完成 | 不可退票 | — | 规则拦截，引导联系客服 |

### 2. 批量退票并发方案

**批量退票请求**：
```json
{
  "order_ids": [10086, 10087, 10088],
  "reason": "行程变更",
  "batch_key": "uuid"   // 批次幂等键（用于去重整个批次）
}
```

**并发控制流程**：
```
  请求到达 → 根据 batch_key 判断是否已处理（Redis SETNX）
     ↓
  获取批量退票锁 lock:batch_refund:{batch_key} (TTL 30min)
     ↓
  逐条处理（goroutine pool, 并发度 5）：
    ① 获取订单锁 lock:order:{order_id} (TTL 30s)
    ② 校验订单状态 + 计算退票费
    ③ 调用 payment-svc 退款
    ④ 更新订单状态
    ⑤ 释放订单锁
    ⑥ 记录退票结果到 Redis List batch_result:{batch_key}
    ⑦ 释放批量退票锁
    ↓
  全部完成 → 生成批量退票报告
    ↓
  推送管理员通知「批量退票完成：成功 N 条 / 失败 M 条」
```

**费用计算规则**：
```
refund_amount = order.paid_amount - order.refund_amount (已退累计)
fee_ratio = 查询阶梯规则(距发车时间差值小时数)
service_fee = refund_amount * fee_ratio
actual_refund = refund_amount - service_fee
batch_total_refund = ∑每单 actual_refund
```

### 3. 并发冲突处理

| 冲突场景 | 处理方式 |
|---------|---------|
| 同一订单被同时申请退票 | 订单锁 `lock:order:{order_id}` 互斥，后到请求返回「该订单正在处理中，请稍后」 |
| 批量退票中单条失败 | 跳过失败条目，继续处理其余；最终报告标记失败原因；管理员可单独重试失败条目 |
| 支付平台退款接口超时 | 重试 3 次（间隔 5s），仍失败标记「退款接口异常」→ 生成人工工单 |
| 订单状态在退票过程中被其他操作变更 | 乐观锁 version 校验，version 不匹配 → 标记「订单状态已变更，请人工复核」 |
| 并发批量退票请求（同一批次） | batch_key 幂等，第二次直接返回上一次的处理结果 |

### 4. 性能保障

| 维度 | 目标 | 手段 |
|------|------|------|
| 批量退票吞吐 | 100 单/批次 ≤30s | goroutine pool 并发 5 |
| 单条退票处理 | ≤500ms | 独立订单锁 + Redis 缓存订单信息 |
| 报告生成 | ≤2s | 退票结果逐条写入 Redis List，完成后一次性聚合 |
| 失败重试 | 每单最多 3 次 | 重试队列 Redis List + 指数退避 |

## 十三、评审结论与落地建议

### 整体评审结论

| 维度 | 评级 | 说明 |
|------|------|------|
| 架构合理性 | A | 三端分离 + 微服务拆分合理，Kratos v3 框架适合微服务架构 |
| 技术栈成熟度 | A | 全部选型均为 Go 生态主流方案，社区活跃，文档完善 |
| 性能设计 | A | 缓存分层、读写分离、异步化、索引优化覆盖所有性能指标 |
| 安全性 | A | HTTPS+AuthMiddleware 权限+幂等+敏感数据加密+审计日志全链路覆盖 |
| 数据一致性 | B | 分布式事务使用 Saga 模式，部分场景存在最终一致窗口 |
| AI 能力 | B+ | Coze API + Go 原生实现，灵活可控，支持工具函数自定义 |
| 运维可观测性 | A | 全链路监控+结构化日志+链路追踪+健康检查完备 |

### 关键建议

1. **优先落地顺序**：用户认证 → 订单系统（核心）→ 派单引擎 → 支付对账 → 班车排班 → AI 助手 → 营销 → 数据分析。建议 MVP 阶段先完成用户+订单+派单+支付，形成业务闭环。

2. **性能压测必须前置**：关键接口（派单/订单搜索/优惠券领取）在上线前完成 Jmeter/Wrk 压测，验证 QPS 指标达标。建议目标：派单引擎 QPS≥200（含 GEO 查询+评分排序），订单搜索 QPS≥500，优惠券领取 QPS≥1000。

3. **数据模型提前规划分表**：`order_main` `transaction_ledger` `dispatch_log` 等核心表预期月增长百万级，建议从首版本即按时间分表，避免后期迁移成本。

4. **AI 模块渐进式投入**：AI 出行助手建议分两期实现——一期先做固定天气预警+快捷指令（直接调用 Coze API），二期完善工具函数体系实现深度对话式交互。

5. **派单引擎灰度机制务必上线前验证**：派单规则直接影响司乘体验，灰度发布+一键回滚机制必须经过充分测试，建议在测试环境模拟新旧规则对比验证。

6. **前端性能关注**：司机端位置上报 H5 在低端机上可能出现卡顿，建议 WebSocket 消息前端做渲染节流（地图 marker 更新≤1s/次），轨迹回放使用 Canvas 而非 DOM 渲染。

7. **安全合规红线**：用户实名信息必须加密存储（AES-256），日志中脱敏展示，非必要不打印。建议上线前通过安全渗透测试。

8. **【新增】统一分布式 ID 替换自增主键**：全部核心业务表主键禁止使用数据库自增 ID，统一替换为雪花算法 64 位全局唯一 ID（见数据库设计章节主键生成策略）。`order_main`、`dispatch_log` 等分表核心表的首版本即使用雪花 ID，避免上线后数据迁移成本。仅 `order_status_log` 等日志子表、`sys_dict` 等静态配置表保留自增 ID。全程禁用 UUID 做主键。
