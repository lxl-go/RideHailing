# 严格 RFC3339 时间 + 缺少失败分支导致「发布」静默失败

## 文档信息
- 创建日期：2026-08-06
- 最近更新：2026-08-06
- 标签：`uni-app`、`gateway`、`RFC3339`、`时间解析`、`异步错误处理`

## 适用场景 / 问题背景
司机端「发布行程」点击后**前端无反应、发布不成功**。表面像网络或接口问题，实际由两个因素叠加导致：
1. 后端对时间字段用**严格 RFC3339** 解析，且**必填 `arrive_time`**；前端只传了空格格式 `2026-08-01 08:30` 的 `depart_time`，完全没传 `arrive_time`。
2. 前端提交函数**只有成功分支**（`if (res.code === 0)` 无 `else`），也没有 `try/catch`——失败时既不提示也不恢复 loading，形成「静默失败」。

## 核心结论
- 「无反应」的本质是**错误被吞掉**，不是请求没发出。修复需两头做：修正 payload 让后端接受，并给前端补失败反馈。
- 同一工程存在两套时间解析策略，是最易踩坑点：
  - 发布**行程** `TripService.PublishTrip` → `parseTime` = `time.Parse(time.RFC3339, v)`，**严格**格式。
  - 发布**需求** `TripService.PublishDemand` → `parseFlexibleTime`，先试 RFC3339，失败再试本地 `2006-01-02 15:04`，**宽容**格式。

## 关键原理

### 1. 严格解析 + 必填字段（`services/trip-service/internal/service/trip.go`）
```go
func parseTime(value string) (time.Time, error) {
    return time.Parse(time.RFC3339, value)
}
func parseFlexibleTime(value string) (time.Time, error) {
    if t, err := time.Parse(time.RFC3339, value); err == nil { return t, nil }
    return time.ParseInLocation("2006-01-02 15:04", value, time.Local)
}
```
`PublishTrip` 对 `depart_time`、`arrive_time` 都走 `parseTime`；任一为空或非 RFC3339 即返回
`InvalidArgument: invalid depart_time / invalid arrive_time`。
合规 RFC3339 示例：`2026-08-01T08:30:00+08:00`（含 `T`、后半 `:ss`、时区偏移 `+08:00`）。

### 2. 网关层字段名（`services/gateway-service/api/gateway/v1/trip.pb.go`）
`PublishTripRequest`：`origin`、`destination`、`depart_time`(3)、`arrive_time`(4)、`seats_total`(5, int32)、`price`(6, float64)。
前端必须带 `arrive_time`，否则后端 `parseTime("")` 直接报错。

### 3. 前端提交「无 else」反模式（`publishTrip.vue` / `publishDemand.vue`）
```js
const res = await publishTrip(payload)
submitting.value = false
if (res.code === 0) { /* success */ }  // 失败什么都不做 → 无反应
```
- 无 `else` → 后端返回错误时 UI 无提示。
- 无 `try/catch` → 网络异常/超时 Promise reject 未被捕获，`submitting` 卡在 true。

## 修复示例
前端时间转换：
```js
const toRFC3339 = (date, time) => `${date}T${time || '00:00'}:00+08:00`
const payload = {
  origin, destination,
  depart_time: toRFC3339(form.depart_date, form.depart_time),
  arrive_time: toRFC3339(form.depart_date, form.arrive_time || form.depart_time),
  seats_total: Number(form.seats) || 4,
  price: Number(form.price) || 0,
}
```
健壮异步提交（必须有失败反馈）：
```js
try {
  const res = await publishTrip(payload)
  if (res.code === 0) { uni.showToast({ title: '发布成功', icon: 'success' }); uni.navigateBack() }
  else { uni.showToast({ title: res.msg || '发布失败', icon: 'none' }) }
} catch (e) {
  uni.showToast({ title: (e && e.msg) || '网络异常，发布失败', icon: 'none' })
} finally {
  submitting.value = false
}
```

## 常见误区 / 注意事项
- **只看占位符格式就以为格式正确**：占位符是给用户看的提示，真实交换格式由后端解析函数决定，两者可能不一致。
- **`submitting.value = false` 务必放 `finally`**，否则请求抛异常时 loading 永久卡住。
- **同一产品不同接口时间格式可能不同**：行程严格、需求宽容，改一条务必核对对应接口用的解析函数。
- **必填字段需逐接口核验**：接单/发布类接口常有多字段必填，漏一个即整请求失败且难被前端察觉。

## 延伸方向
- 后端统一时间解析（全部走 `parseFlexibleTime`）可规避这一整类「格式不一致」问题，但要评估对存量非法格式的容忍度。
- 前端可封装通用 `submitWithFeedback` 工具，统一成功/失败/异常三态，避免每个页面重复手写。
