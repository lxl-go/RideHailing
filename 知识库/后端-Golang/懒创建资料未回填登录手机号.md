# 登录成功但资料手机号为空：懒创建 EnsureXxx 未回填登录手机号

- 创建日期：2026-08-07
- 最近更新：2026-08-07
- 标签：微服务、账号与资料分离、懒加载、数据回填、proto 演进、Kratos

## 适用场景 / 问题背景

乘客端用「手机号 + 短信验证码」登录成功（`auth_user.principal` 里存了手机号），
但个人中心一直显示「未绑定手机」（`profile.mobile` 为空）。

排查链条：UI `profile?.mobile || '未绑定手机'` → `loadProfile()` 拉 `/carpool/passengers/me`
→ 网关转发到 passenger-service → 内部 `EnsurePassenger(userID)` 懒创建资料行。

根因：账号（auth-service 的 `auth_user`）与资料（passenger-service 的 `passenger_profile`）分属不同服务。
资料行由「首次访问 /me」时懒创建，创建时只写 `id` 和默认昵称，**从不带手机号**。
登录接口只返回 `user_id`，手机号（principal）停留在 auth 侧，从未同步到资料表。

## 核心结论

- 手机号应登录成功后立刻回填到资料表（`passenger_profile.phone`），而不是等用户手动编辑资料。
- 回填要做成「幂等 + 兜底」：创建时带上 phone；已存在但 phone 为空的旧行，下次 Ensure 时自动补齐；已有 phone 则不动。
- 手机号来源只有一处——登录请求的 `principal`，所以要把它从网关登录入口一直传到资料服务的 `EnsureXxx` RPC。
- 回填失败**不得**阻断登录（资料服务挂了不能让用户登录失败），记录 warning 即可。

## 关键原理

### 调用链（网关为编排层）

```
POST /carpool/auth/login
  → authSvc.Login() 成功，拿到 reply.user_id
  → (role=passenger) passengerSvc.EnsurePassenger(userID, principal)   // 新增 phone 参数
      → biz.Usecase.EnsurePassenger(ctx, id, phone)
          → data client → passenger-service gRPC/HTTP EnsurePassengerRequest{id, phone}
              → biz: 已有行且 phone 空 → Update 补齐；无行 → Create(带 phone)
```

### EnsureXxx 的幂等回填写法

```go
func (uc *PassengerUsecase) EnsurePassenger(ctx, id int64, phone string) (*PassengerProfile, error) {
    phone = strings.TrimSpace(phone)
    profile, err := uc.repo.GetByID(ctx, id)
    if err == nil {
        if phone != "" && strings.TrimSpace(profile.Phone) == "" { // 只补空，不覆盖已有
            profile.Phone = phone
            if err := uc.repo.Update(ctx, profile); err != nil { ... }
        }
        return profile, nil
    }
    if !errors.Is(err, ErrPassengerNotFound) { return nil, err }
    profile = &PassengerProfile{ID: id, Nickname: fmt.Sprintf("Passenger %d", id), Phone: phone, Status: Enabled}
    if err := uc.repo.Create(ctx, profile); err != nil { ... }
    return profile, nil
}
```

### proto 演进（加字段向后兼容）

`EnsurePassengerRequest` 加 `string phone = 2;` 是向后兼容的：
- 老客户端只发 `id`，phone 为空 → 创建行 phone 为空，走旧逻辑；
- 新客户端带 phone → 新老服务都能识别（未知字段会被忽略/保留，不影响解析）。

改完 `.proto` 用 Makefile 目标重新生成三种产物：
`--go_out`(结构体) `--go-grpc_out`(gRPC 桩) `--go-http_out`(HTTP 绑定)，参数 `paths=source_relative`。

### 网关登录处理器里「非致命回填」

```go
reply, err := authSvc.Login(ctx, req)
if err == nil && reply.GetUserId() > 0 {
    switch req.GetRole() {
    case "passenger":
        if _, seedErr := passengerSvc.EnsurePassenger(ctx, reply.GetUserId(), req.GetPrincipal()); seedErr != nil {
            zap.L().Warn("seed passenger phone failed", ...) // 登录不失败
        }
    case "driver":
        // 同样处理 EnsureDriver
    }
}
return returnData(ctx, reply, err)
```

## 示例

资料侧（passenger-service）响应 `passenger.phone` 为空的原因，可从三个层面验证：
1. 数据库：`SELECT phone FROM passenger_profile WHERE id=<user_id>` 是否为空；
2. 网关：登录后是否调用了 `EnsurePassenger`（看网关日志有无 "seed passenger phone failed"）；
3. 前端：`normalizePassenger` 中 `mobile: item.mobile ?? item.phone`，后端 `phone` 字段名为 `phone`，映射本身正确。

## 常见误区 / 注意事项

- 只改资料服务的 `UpdatePassenger` 接口去补 phone 不可靠：UI 不一定会主动调用，且 Update 是全量覆盖（空值会清掉昵称等其它字段）。
- 不要把手机号塞进 JWT 再在 `/me` 时读取：改动面大（发 token、解析、CurrentUser 全链路），且刷新 token 后仍需一致性。登录入口直接回填更简单。
- 回填时只覆盖「空 phone」，避免把用户后来自己改的号码覆盖回登录 principal（存在换绑场景）。
- Ensure 里更新行用 `repo.Update`，注意该实现若 `RowsAffected==0` 会报 NotFound，幂等调用可接受。
- 司机端 `EnsureDriver` 是同一套坑：`driver_profile.phone` 也一样空，需同步修复，否则司机端同样显示异常。

## 延伸方向

- 换绑手机号流程：登录 principal 变化后，需要专门的换绑接口同时改 `auth_user.principal` 与资料表 phone，并保证事务/一致性。
- 可考虑登录成功事件（消息队列）驱动资料预热，解耦网关，而不是在 HTTP 处理器里同步编排。
- 把 Ensure + 回填逻辑抽成公共 SDK，供乘客、司机两个服务复用，减少重复代码。
