# 司机发布行程链路排查：地点校验匹配逻辑、网关吞错与 15 分钟竞态

- 创建日期：2026-08-09
- 最近更新：2026-08-09
- 标签：微服务、网关、错误透传、高德地图、前端校验、故障排查、多根因叠加
- 关联：见《网关类型断言仅部分客户端实现导致服务未配置.md》（同属发布行程链路，前一个 bug）

## 适用场景 / 问题背景

司机端「发布行程」失败，页面提示「服务开小差了，请稍后重试」，网关日志：
`gateway request failed ... "error":"trip service returned status 400"`。
此时上一轮「地点校验服务未配置」（网关缺 HTTP 客户端方法）已修复，7 个服务都在跑，
说明错误已从「网关没实现」推进到「下游真的返回 400」，但**网关把 400 吞成了 500 兜底文案**，
用户和开发都看不到真实原因。

## 核心结论

一层层向下扒，最终是三个问题叠加：

1. **网关 HTTP 客户端吞掉下游错误体**（trip `execute` 用 `fmt.Errorf("trip service returned status %d")`，
   不解析下游响应体）→ 下游 400/503 一律变成 500「服务开小差了」。这是「看不到真实原因」的直接原因。
2. **`ValidateLocation` 匹配逻辑与前端用法矛盾**：前端只发 `{keyword: 地名, location: {name: 地名}}`（无坐标、无 poi_id），
   后端却要求 `poi_id` 或「名称+坐标」精确匹配 → 永远返回 400 `location could not be verified`。
3. **出发时刻 15 分钟竞态**：前端默认 `now+15min` 压线，服务端严格校验 `depart >= now+15min`，
   表单填写耗时或双端时钟偏差都会触发 400 `departure must be at least 15 minutes from now`。

## 关键原理

### 排查顺序：先让错误“看得见”

网关把下游 4xx/5xx 统一转成 500 兜底文案后，一切错误都长得一样。两步拨云见日：

- **绕过网关直连下游**：`curl http://127.0.0.1:9040/v1/driver/trips/locations/validate` 直接看下游真实返回。
- **用 `curl.exe -i` 而非高层封装**：PowerShell `Invoke-WebRequest` 对 4xx/5xx 抛异常且体读取不可靠，
  容易把真实 400 误判成 503；`curl -s -i` / `-w "%{http_code}"` 更稳。
- 首次直连得到 503（启动期/旧进程），稳定后得到 400 → 说明是业务校验失败而非服务不可用。

### 网关错误透传的正确姿势

其他客户端（auth/passenger/driver）都用 `newUpstreamHTTPError(statusCode, body)` 封装下游错误，
网关 `gatewayErrorStatusAndMessage` 据此把状态码与 message 透传出去。trip 客户端要一致：
```go
if resp.StatusCode >= 400 {
    body, _ := io.ReadAll(resp.Body)
    return newUpstreamHTTPError(resp.StatusCode, body)
}
```
这样下游 400 → 网关 400 + 真实 message，不再无脑 500。

### 校验逻辑要匹配调用方数据能力

`ValidateLocation` 的本意是「输入 → 解析出标准地点（poi_id/坐标/标准名）」，前端恰好只有地名，
没有可“校验”的坐标。于是匹配策略应是：
- `poi_id` 命中 → 精确返回；
- 有坐标时名称+坐标精确命中 → 精确返回；
- 否则（仅名称）→ 返回搜索结果最佳候选（`locations[0]`），完成“地名解析”。

把“必须精确匹配否则报错”改成“有依据精确匹配、无依据解析兜底”，才与前端使用方式自洽。

### 幂等 request_id 与业务字段

发布接口还有一处易踩的坑：`PublishTripCommand.Origin/Destination` 取自
`req.Origin.FormattedAddress`（不是 name）。前端兜底 `{name, formatted_address: name}` 恰好满足；
若漏传 formatted_address，会返回 400 `invalid trip`。

## 解决方案

- trip-service `ValidateLocation`：改为「poi_id 精确 → 名称+坐标精确 → 最佳候选兜底」，
  抽 `locationToReply(location)` 复用返回构造。
- gateway `TripHTTPClient.execute`：>=400 用 `newUpstreamHTTPError` 透传状态码与 message。
- 前端 `publishTrip.vue`：默认 `depart_time` 从 `now+15min` 改为 `now+30min`，避免 15 分钟压线竞态。

## 验证方式

```bash
# 1) 直连下游，逐段确认
curl -s -X POST http://localhost:9040/v1/driver/trips/locations/validate \
  -H "Content-Type: application/json" -d '{"keyword":"北京站","location":{"name":"北京站"}}'
# => 200, {"location":{"poiId":"B000A83C36","name":"北京站",...,"longitude":116.427354,"latitude":39.90283}}

# 2) 报价
curl -s -X POST http://localhost:9040/v1/driver/trips/price-preview \
  -H "Content-Type: application/json" \
  -d '{"origin":{"name":"北京站","longitude":116.427281,"latitude":39.902727},
       "destination":{"name":"西单","longitude":116.374221,"latitude":39.907708},
       "depart_time":"<RFC3339 一小时之后>"}'
# => 200, routeDistanceMeters + price

# 3) 发布（origin/destination 的 formatted_address 必须非空；driver_id 必须 >0）
curl -s -X POST http://localhost:9040/v1/driver/trips -H "Content-Type: application/json" -d '{...}'
# => 200, {"tripId":"...","status":10,"price":17.56,...}

# 4) 网关侧：未带 token 访问 /carpool/trips/locations/validate 应返回 401（路由已注册）
```
注意：PowerShell 向 curl 传含中文 JSON 时，用文件 `--data-binary "@xxx.json"` 且文件须为**无 BOM 的 UTF-8**，
否则 protojson 报 `syntax error ... invalid value`。

## 常见误区 / 注意事项

- 「服务开小差了」不等于服务宕机：它是网关兜底，先直连下游看真实状态码。
- 网关 HTTP 客户端必须透传下游错误，否则下游业务校验失败（400）会被误报成 500，误导排查方向。
- 校验逻辑要与调用方的数据能力匹配：前端给不出坐标时，别要求“坐标精确匹配”。
- 测试数据要清理：发布探针会在库里留行程，测完软删（DELETE 接口 / `is_deleted=1`）。
- 前端压线默认值（如“恰好 +15 分钟”）极易踩服务端严格校验的竞态，默认值应留缓冲。

## 延伸方向

- 网关统一封装所有下游 HTTP 客户端的错误（已有 `newUpstreamHTTPError`，确保各客户端都用上），
  并考虑把下游 message 翻译为中文提示，而非直接透传英文。
- `ValidateLocation` 可加候选列表返回，让前端做选点，而不是后端单点兜底。
- 出发时间校验可放宽为「允许 15 分钟内的缓冲」或由前端默认值 +30min 统一规避。
