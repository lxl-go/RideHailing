# 登录成功但首页/订单/我的报「服务开小差」：下游微服务未启动

- 创建日期：2026-08-07
- 最近更新：2026-08-07
- 标签：微服务、网关、服务编排、服务未启动、故障排查、区分根因

## 适用场景 / 问题背景

乘客端能用「手机号 + 短信验证码」登录成功（说明网关 + auth-service 正常），
但登录后点击「首页 / 订单 / 我的」都提示「服务开小差了，请稍后重试」。

首页打 `trip-service`，订单打 `order-service`，我的则打 `passenger-service`（资料）与 `trip-service`（优惠券）。
这三个页面背后是三个不同的下游微服务，全部报同一句 500，而鉴权（auth）却工作是关键线索。

## 核心结论

- 这不是代码 bug，而是**下游微服务没启动**。
- 「服务开小差了」是网关 `http.go` 的默认兜底文案：只要「网关调用某下游」发生了连接失败 / 下游返回 5xx / 无法解码，就走 `fallbackChineseMessage("")` 返回 HTTP 500 这句文案。
- 登录能成功，是因为登录只依赖网关 + auth-service（这两个起来了）；
  而首页/订单/我的各自依赖 trip/order/passenger 服务，它们没起来 → 网关连不上 → 500 → 该文案。
- 根因判定的二分工：**哪些服务起来了，它能用；哪些没起来，它就报错**。

## 关键原理

### 一句文案对多个根因

「服务开小差了」是最笼统的一档兜底，落到它的原因很多，必须区分：

| 场景 | 表象 | 真正原因 |
| --- | --- | --- |
| protojson 解码失败 | 下游返回 200，网关却 500 | 网关 HTTP 客户端用 `encoding/json` 解码 protojson（int64=字符串） |
| **下游未启动** | 网关连不上下游 | 微服务进程没跑 / 端口不通 → 网络错误 |
| 下游本身 5xx | 下游返回内部错误 | 下游 DB / 业务异常 |

所以「看到服务开小差」不等于「代码有 bug」，第一步先看网关日志里 `gateway request failed` 的 `error` 到底是谁：
`connection refused` → 服务没起来；`cannot unmarshal string into ... int64` → protojson 解码问题。

### 用 netstat 二分定位

```powershell
netstat -ano | findstr LISTENING | findstr ":9000 :9010 :9020 :9030 :9040 :9050 :9060"
```

网关默认 `:9000`，各下游 `auth:9010 passenger:9020 driver:9030 trip:9040 order:9050 review:9060`（见 gateway `configs/config.yaml` 的 `clients.http_base_url`）。
哪几个端口没监听，对应哪几个页面会 500。

### 绕过网关直调下游确认服务健康

```powershell
(Invoke-WebRequest "http://127.0.0.1:9040/v1/trips?page=1&page_size=5").Content
# => HTTP 200, {"total":"0","items":[]}  说明 trip 服务本身正常
```

## 同根因的另一种表象：UI 控件「用不了 / 自己弹回」

同一根因（下游未启动）在移动端还有完全不同的观感：**开关/按钮点了没反应或立即弹回**，
容易误判成前端 bug，实际是接口失败后前端按设计「回滚状态」。

### 司机端在线/离线开关实例

- 司机首页 `home.vue` 的 `u-switch v-model="userStore.online" @change="toggleOnline"`。
- `toggleOnline(val)` 调用 `PUT /carpool/drivers/me`（body `{service_status: val ? 2 : 1}`），
  `request.js` 对**网络失败**返回 `{code:-1}`，然后 `if (res.code !== 0) userStore.setOnline(!val)` 把开关弹回离线。
- 于是后端没起时表现就是「怎么拨都一直是离线、开关用不了」，且因为 `silent:true`，连 toast 都不弹，
  看起来更像纯前端问题。

### 通用排查套路：状态回滚型交互

1. 找 UI 上「拨动后自动回弹/闪一下」的控件，定位它绑定的事件处理器（如 `@change`）。
2. 看处理器里是否有「失败回滚」逻辑（`if code !== 0 setState(!val)`）。
3. 回滚 = 接口没成功。再按「服务开小差」那套二分：`netstat` 查端口 → 直连下游测接口。
4. 确认代码链路本身没问题后（路由/权限/客户端映射），直接对下游服务做一次
   `PUT` + `GET` 验证持久化，可先用数据库里真实的一行、测完再还原。

### 本次端到端验证方法（绕开前端直接测后端链）

```powershell
# 1. 7 个端口全部监听（见上方 netstat 命令）
# 2. 网关鉴权生效：未带 token 应返回 401
(Invoke-WebRequest "http://localhost:9000/carpool/drivers/me").StatusCode  # => 401
# 3. 绕过网关直连 driver-service 验证 service_status 持久化（无鉴权）
Invoke-WebRequest -Uri "http://localhost:9030/v1/drivers/3" -Method PUT `
  -ContentType 'application/json' -Body '{"service_status":2}'
(Invoke-WebRequest "http://localhost:9030/v1/drivers/3").Content  # => "serviceStatus":2
# 4. 落库确认后再还原为 1
Invoke-WebRequest -Uri "http://localhost:9030/v1/drivers/3" -Method PUT `
  -ContentType 'application/json' -Body '{"service_status":1}'
# 5. MySQL 在 docker 容器里时用 docker exec 查
docker exec <mysql容器> mysql -uroot -proot 01ride -e "SELECT id, service_status FROM driver_profile;"
```

后端开关链路核对结论（供快速复核）：网关 `PUT /carpool/drivers/me` → 权限 `driver:profile:update_self`
（RBAC 已授权给司机角色）→ 网关 `DriverHTTPClient` `PUT /v1/drivers/{id}` → driver-service
`UpdateDriver` → biz 校验 `service_status` 合法（1/2/3）→ `profileToRecord` 含 `ServiceStatus` → 落库。
GET 侧 `GET /carpool/drivers/me` 走 `EnsureDriver` 返回 `service_status`，前端 `st === 2` 判在线。

## 正确启动顺序

先起依赖，再起网关。基础设施（MySQL:3306、Redis:6379 等）需在线。各服务均在对应目录执行 `go run ./cmd/<服务名>`：

```bash
# 每个窗口启动一个（共有 7 个）
cd services/auth-service      # go run ./cmd/auth
cd services/passenger-service # go run ./cmd/passenger
cd services/driver-service    # go run ./cmd/driver
cd services/trip-service      # go run ./cmd/trip
cd services/order-service     # go run ./cmd/order
cd services/review-service    # go run ./cmd/review
cd services/gateway-service   # go run ./cmd/gateway   # 最后起
```

## 常见误区 / 注意事项

- 只跑网关 + auth 去测「登录」会得到“验证码/登录成功”的假象，随后所有数据页全 500；请把 7 个服务全部起齐再测。
- 别把「服务开小差」直接等同于 protojson bug：protojson 那个坑是「直连下游 200、经网关 500」，而「服务没起」是「直连下游就拒绝连接」。两者验证方式不同。
- 服务启动时若打印 `FATAL`/`exit status`，先看它依赖的连接（DB/Redis）是否可达，而不是怀疑 HTTP 层。
- 改动 `.proto` 后要重新生成绑定，且**所有服务用同一批生成代码**，否则网关与下游字段对不上也会出现疑似 500。

## 延伸方向

- 可给网关「服务开小差」兜底加更精确文案/错误码，区分「依赖不可用」与「内部错误」，便于运维一眼定位。
- 为本地起 7 个服务写一个一键启动脚本（`make dev` / docker-compose），杜绝“漏起某服务”。
